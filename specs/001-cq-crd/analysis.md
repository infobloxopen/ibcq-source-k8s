#### ✅ RESOLVED: Schema Column Mismatch

**Issue**: Specification mentioned 14 columns including `_cq_id` and `_cq_parent_id` (SC-002), but implementation plan didn't clarify these are SDK-generated.

**Impact**: HIGH - Table schema clarity

**Resolution APPLIED**:
- Updated spec (SC-002) to clarify: "plus CloudQuery SDK columns (_cq_id, _cq_parent_id auto-generated)"
- Updated plan to note: "CloudQuery SDK automatically adds _cq_id and _cq_parent_id columns via transformers"
- These columns are automatically added by CloudQuery SDK when using `transformers.WithPrimaryKeys("UID")`

**Status**: ✅ FIXED - Clarified in spec and plan

---

#### ✅ RESOLVED: Configuration Format Inconsistency

**Issue**: Spec showed three different configuration approaches (Options A, B, C) but plan used different format

**Resolution APPLIED**:
- **Chosen Format**: Compact string format with GVK: `"group/version/kind"`
- Updated spec to remove multiple options, document single chosen approach
- Configuration now consistent across all documents:
  ```yaml
  custom_resources:
    - gvk: "cert-manager.io/v1/Certificate"
      namespaces: ["default", "production"]  # optional
  ```
- Added validation pattern: `^[a-z0-9.-]+/[a-z0-9]+/[A-Z][a-zA-Z0-9]*$`
- Future enhancements (wildcards, exclude) documented separately

**Rationale**:
- Compact: Single string vs three fields
- Standard: Matches Kubernetes GVK notation
- Simple: Easy to parse with single regex
- Extensible: Can add wildcards later

**Status**: ✅ FIXED - Single format chosen and documented

#### 🟡 MEDIUM: Pluralization Strategy Unclear

**Issue**: Open question about resource name pluralization not resolved

**From Plan Open Questions**:
> Should we fetch resource names from CRD definitions instead of hardcoding pluralization rules?
> Decision: Start with simple pluralization, fetch from CRD if not found

**Current Approach in Plan**:
```go
func pluralize(kind string) string {
    // Simple pluralization (can be enhanced)
    // TODO: Use proper pluralization logic or fetch from CRD
}
```

**Risk**: Simple pluralization will fail for irregular plurals (e.g., Ingress → Ingresses not Ingresss)

**Impact**: MEDIUM - Some CRs won't be fetchable without proper pluralization

**Recommended Approach**:
1. **Phase 1**: Use hardcoded map for common irregular plurals:
   ```go
   var irregularPlurals = map[string]string{
       "Ingress":   "ingresses",
       "Endpoints": "endpoints",
       "Status":    "statuses",
       // Add more as discovered
   }
   ```
2. **Phase 1**: Fallback to simple rules (add 's', 'y'→'ies', etc.)
3. **Phase 2/3**: Fetch from CRD definition using `crd.Spec.Names.Plural`

**Action Required**: Add Task 4.1.5: Create irregular plurals map

#### 🟡 MEDIUM: Error Handling Strategy Incomplete

**Issue**: Error handling approach mentioned but not fully specified

**From Plan (Fetcher Implementation)**:
```go
// Error handling: log errors but continue with other resources
```

**Missing Details**:
- What errors are retryable vs fatal?
- Should we return partial results on error?
- How to communicate errors to users?
- Should sync fail or warn on permission errors?

**Recommendation**: Define error handling policy:

**Error Categories**:
1. **Fatal Errors** (fail entire sync):
   - Invalid configuration
   - Unable to initialize dynamic client
   - Unable to connect to cluster

2. **Resource-Level Errors** (log and continue):
   - CRD doesn't exist
   - Permission denied for specific CR type
   - Invalid resource data

3. **Item-Level Errors** (log and skip item):
   - Malformed CR object
   - JSON marshaling failure

**Action Required**: Add error handling specification to plan, update Task 4.5
